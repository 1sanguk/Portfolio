과제

  • 로그인 안정화
  • 광장/빌리지 채널 분산

  • 대용량 조회 최적화
  • 운영툴 설계

해결 과정

  1. 로그인 병목: 락 경합을 줄이고 독립 작업을 병렬로

    로그인 과정에서 API마다 걸린 락 때문에 요청이 직렬로 처리되는 병목을 확인했습니다. 요청 전체를 막던 락 경합을 줄이고 서로 영향을 주지 않는 작업을 분리해 병렬로 처리했습니다. 남은 병목은 DB 커넥션 풀 확충과 누락된 인덱스 추가로 해소했습니다.

  2. 채널 풀: 인원이 가장 적은 채널로 배치

    광장과 빌리지에 기본 5개의 채널 풀을 두고, 신규 유저를 인원이 가장 적은 채널에 배치하는 분산 로직을 설계했습니다. 채널별 유저 상태를 격리해 같은 채널의 유저끼리만 상호작용하도록 구성했습니다. 동시 접속 때 채널별 인원 카운터가 꼬이는 경쟁 상태(race condition)는 Go의 sync.Mutex로 보호했습니다.

  3. 자동 증설: 25/30명에서 5개 채널을 한 번에

    전체 채널이 정원 30명 중 25명에 가까워지면 채널 5개를 자동으로 일괄 증설하도록 구현했습니다. 증설 직후 유저가 새 채널로 한꺼번에 몰리는 부하 폭주(thundering herd)를 막기 위해 신규 유저는 점진적으로 나눠 배치했습니다. 정원 30명은 실제 플레이 블라인드 테스트로 검증해 확정했습니다.

  4. 채팅 서버 확장과 빌리지, 지적도 신규 개발

    기획팀과 스펙을 협의한 뒤 코코마인 산리오 캐릭터즈에서 만든 채팅 서버를 코코마인에 맞게 다시 설계했습니다. 빌리지와 지적도 서버는 새로 추가하고, 빌리지 안의 인터랙티브 아이템, 상호작용 모션, 주소 시스템을 함께 만들었습니다.

  5. 랭킹: Redis에 실시간 반영

    코코마인 산리오 캐릭터즈에서 Redis로 전환한 랭킹 구조를 바탕으로, 기부 기여도와 패션매치 점수를 Redis에 실시간으로 반영하고 조회는 페이징과 Redis 캐싱으로 처리했습니다.

  6. 운영툴과 조회 최적화

    운영팀 담당자와 필요한 기능을 협의해 요구사항을 확정하고 ASP.NET Core 기반 운영툴을 설계, 개발했습니다. 렉이 생기는 구간에는 인덱싱과 쿼리 최적화를 적용해 아이템과 랭킹처럼 큰 데이터의 조회와 갱신 시간을 5~15초에서 2~6초로 줄였습니다.

결과

  • 로그인 처리 시간 30초~3분에서 10~30초, 아이템과 랭킹 데이터 처리 5~15초에서 2~6초로 단축
  • 광장과 빌리지의 1채널 과밀을 최소 부하 배치와 자동 증설로 완화
  • 유저 간 채팅, 빌리지, 지적도 등 상호작용 콘텐츠 확장

해결 과정

  1. 결제: 재시도해도 두 번 지급되지 않게

    네트워크 지연으로 결제가 실패하면 자동으로 재시도하는 로직을 추가했습니다. 재시도 전에는 이전 결제 내역과 지급 내역을 대조해 이미 지급된 건을 다시 지급하지 않도록 했고, 결제는 완료됐지만 아이템이 지급되지 않은 건은 안전하게 복구하도록 구현했습니다.

  2. MySQL 5.7에서 8.0으로

    인증 방식과 GROUP BY 처리처럼 8.0에서 호환성이 깨지는 부분을 찾아 소스 코드를 수정하고, 테스트를 거쳐 배포했습니다. 주요 쿼리에는 인덱싱과 최적화를 함께 적용했습니다.

기술 관리

AI가 작성한 코드는 실행 여부뿐 아니라, 기존 기능을 깨뜨리지 않는지, 유지보수 가능한 구조인지, 민감정보와 비밀키가 노출되지 않는지 확인한 뒤 반영합니다.

유지보수와 요구사항

  • 배포 대상별로 폴더를 나눠(API 서버, GPU 추론 서버) 한쪽을 고쳐도 다른 쪽이 흔들리지 않게 했습니다.
  • AI가 만든 코드도 기존 스타일을 따르고, 정적 검사(ruff)를 통과해야 반영합니다.
  • 다먹자 AI는 구현 전에 8단계 설계 문서를 쓰고 모두 승인받은 뒤 그 범위 안에서만 만들었습니다.

기능이 정확한지 확인하기

  • 사진 분류, OCR, 상품명 매칭, 오류 처리 등 주요 기능마다 자동 테스트를 만들었습니다. API·전처리 서버 110개와 모델 실행 서버 34개, 총 144개를 코드 변경 때마다 실행해 기존 기능이 깨지지 않았는지 확인합니다.
  • 직접 정답을 적은 골든셋과, 개선할 때 보지 않은 홀드아웃을 나눠 평가합니다.
  • 엔진 설정을 바꾸면 36장의 읽은 글자가 이전과 같은지, 규칙을 바꾸면 다른 영수증 결과가 그대로인지 다시 돌립니다.
  • Giftie의 외부 API는 이미지 입력과 직접 입력 두 개만 공개하도록 설계했습니다. 자동 테스트에서 공개된 엔드포인트 목록을 확인해, 내부용 추천 API가 실수로 다시 노출되는 것을 방지합니다.

운영 환경의 실패에 대비하기

  • 모델 응답이 항상 올바른 형식으로 온다고 가정하지 않습니다. 쉼표가 빠진 JSON 때문에 분석 전체가 중단된 사례를 바탕으로, 응답 복구 처리와 같은 오류가 다시 발생하는지 확인하는 회귀 테스트를 추가했습니다.
  • GPU 서버가 일시적으로 응답하지 않으면 제한된 횟수만 재시도하고, 계속 실패할 때는 사용자가 직접 입력할 수 있도록 전환합니다.
  • AI가 작성한 배포 문서는 실제 실행 절차와 대조합니다. API 서버만 실행하고 모델 서버(Ollama)를 빠뜨린 내용을 발견해, 실행 순서와 단계별 확인 방법을 문서에 추가했습니다.

보안

  • 영수증의 카드 번호와 전화번호는 저장하거나 기록에 남기기 전에 지웁니다.
  • 상태 확인용 주소 하나를 빼고 모든 AI 서버 요청은 내부 API 키로 인증하고, 사진은 저장소의 임시 주소로만 주고받습니다.
  • 비밀키는 코드에 쓰지 않고, git push처럼 되돌리기 어려운 작업은 AI가 하지 못하게 규칙으로 막아 직접 합니다.

의도 관리

하나의 프롬프트에 모든 맥락을 넣지 않습니다. 공통 규칙, 역할별 계약, 작업 체크리스트, 검증 명령을 연결한 하네스로 AI가 필요한 지침만 읽고 일하게 합니다.

역할별 문서로 구성한 AI 하네스

  • 진입점: Agents.md에는 프로젝트 구조, 공통 코딩 규칙, 금지 사항과 어떤 세부 문서를 읽어야 하는지 적어 하네스의 라우터로 사용합니다.
  • 역할별 계약: 제품 요구사항, 아키텍처, API·데이터 계약, 도메인 규칙, UI/UX, 보안, 운영과 테스트 기준을 별도 문서로 나눕니다. 백엔드 작업자는 데이터 정합성과 동시성 규칙을, AI 작업자는 입력·출력과 평가 기준을, UI 작업자는 화면 명세를 우선 읽습니다.
  • 작업별 컨텍스트: AI에 전체 문서를 매번 주지 않고 현재 변경과 연결된 문서와 코드만 읽게 합니다. 경계를 건드리면 연관 문서를 추가로 불러와 서로 다른 역할의 전제까지 확인합니다.
  • 상태와 검증: 작업 체크리스트에 미착수·진행·완료 상태와 근거를 남기고, 백엔드·프론트엔드·데이터·통합 테스트를 변경 유형에 맞는 승인 게이트로 연결합니다.
  • 권한 제어: 탐색은 읽기 전용, 구현은 지정 파일만 수정하게 하며 비밀키 접근·외부 전송·배포처럼 영향이 큰 작업은 차단하거나 직접 승인합니다.

프로젝트마다 다른 작업 방식

  • C++ 서버는 실력을 쌓는 것이 목적이라, AI는 코드를 대신 쓰지 않고 힌트와 리뷰만 하도록 규칙을 정했습니다. 코드는 직접 짜고, AI는 버그와 설계 문제를 짚습니다.
  • 다먹자와 Giftie는 구현까지 적극적으로 맡기되, 요구사항을 수용 기준이 분명한 작은 작업으로 나누고 한 번에 한 기능이나 한 문제만 맡깁니다.
  • 계획·탐색·구현·검증 에이전트에 역할과 소유 파일을 분명히 나누고, 백엔드·AI·UI처럼 서로 독립적인 작업은 병렬로 실행합니다. 각 에이전트는 자기 역할의 세부 문서를 따르고, 공유 타입이나 API 경계 변경은 통합 단계에서 다시 대조합니다.
  • AI가 만든 변경은 diff로 읽으며 비즈니스 규칙, 동시성, 데이터 정합성, 보안 경계가 유지되는지 코드 리뷰합니다.
  • 완료 기준은 코드 생성이 아니라 단위·통합·회귀 테스트와 성능 지표 통과이며, 실패하면 원인을 좁혀 다시 작업시킵니다.

문서가 다음 작업의 실행 상태가 되게

  • C++ 서버는 버전마다 피드백을 문서로 남기고 "미적용, 완료, 의도적 유지"로 상태를 관리합니다. 원래 지적은 지우지 않고 아래에 "보완 내용"을 쌓도록 규칙 자체를 고쳐 나갔습니다.
  • 다먹자는 설계 문서와 실험 기록을 다음 작업의 출발점으로 삼아, 새 세션에서도 같은 기준으로 이어서 작업합니다.
  • 구현이 바뀌면 관련 요구사항·아키텍처·API 문서와 작업 체크리스트를 함께 갱신합니다. 다음 AI는 대화 기록이 없어도 문서의 현재 상태와 남은 검증 항목에서 바로 이어서 작업합니다.

범위를 좁혀 나눠 맡기기

  • Giftie에서 AI가 만든 API가 세 개였는데, 개발용 추천 API가 공개된 채 남아 있던 것이었습니다. 이미지 입력과 직접 입력 두 개로 정리하고 추천은 내부 기능으로 돌렸습니다.
  • 직접 입력과 사진 입력을 같은 형식으로 바꾸는 기준을 먼저 정해, 기록, 일정, 알림, 추천을 팀원과 나눠 만들 수 있게 했습니다.
