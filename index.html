  • 광장/빌리지 채널 분산

해결 과정

  1. 로그인 병목: 락 경합을 줄이고 독립 작업을 병렬로

    로그인 과정에서 API마다 걸린 락 때문에 요청이 직렬로 처리되는 병목을 확인했습니다. 요청 전체를 막던 락 경합을 줄이고 서로 영향을 주지 않는 작업을 분리해 병렬로 처리했습니다. 남은 병목은 DB 커넥션 풀 확충과 누락된 인덱스 추가로 해소했습니다.

  2. 채널 풀: 인원이 가장 적은 채널로 배치

    광장과 빌리지에 기본 5개의 채널 풀을 두고, 신규 유저를 인원이 가장 적은 채널에 배치하는 분산 로직을 설계했습니다. 채널별 유저 상태를 격리해 같은 채널의 유저끼리만 상호작용하도록 구성했습니다. 동시 접속 때 채널별 인원 카운터가 꼬이는 경쟁 상태(race condition)는 Go의 sync.Mutex로 보호했습니다.

  3. 자동 증설: 25/30명에서 5개 채널을 한 번에

    전체 채널이 정원 30명 중 25명에 가까워지면 채널 5개를 자동으로 일괄 증설하도록 구현했습니다. 증설 직후 유저가 새 채널로 한꺼번에 몰리는 부하 폭주(thundering herd)를 막기 위해 신규 유저는 점진적으로 나눠 배치했습니다. 정원 30명은 실제 플레이 블라인드 테스트로 검증해 확정했습니다.

  4. 채팅 서버 확장과 빌리지, 지적도 신규 개발

    기획팀과 스펙을 협의한 뒤 코코마인 산리오 캐릭터즈에서 만든 채팅 서버를 코코마인에 맞게 다시 설계했습니다. 빌리지와 지적도 서버는 새로 추가하고, 빌리지 안의 인터랙티브 아이템, 상호작용 모션, 주소 시스템을 함께 만들었습니다.

  5. 랭킹: Redis에 실시간 반영

    코코마인 산리오 캐릭터즈에서 Redis로 전환한 랭킹 구조를 바탕으로, 기부 기여도와 패션매치 점수를 Redis에 실시간으로 반영하고 조회는 페이징과 Redis 캐싱으로 처리했습니다.

  6. 운영툴과 조회 최적화

    운영팀 담당자와 필요한 기능을 협의해 요구사항을 확정하고 ASP.NET Core 기반 운영툴을 설계, 개발했습니다. 렉이 생기는 구간에는 인덱싱과 쿼리 최적화를 적용해 아이템과 랭킹처럼 큰 데이터의 조회와 갱신 시간을 5~15초에서 2~6초로 줄였습니다.

결과
