About

I fix the structure,
not the symptom.

Over 4 years as a game server and backend developer, I've built hands-on experience that spans far beyond maintenance and new features, covering performance optimization, operational infrastructure, and real-time server design. Directly responsible for live services running across Korea, Japan, Taiwan, and English-speaking regions, I've tracked down and resolved issues that cut straight to the heart of stability and performance: eliminating login bottlenecks, migrating ranking systems to Redis, building a chat server from the ground up, stabilizing payments, and executing DB migrations.

Years of incident response and structural refactoring have reinforced one conviction: patching surface symptoms is a temporary fix, but understanding the root cause and redesigning the structure is what actually lasts. Backend work happens entirely out of sight, but the quieter the server, the more freely users stay immersed, and the more the operations team can focus on building rather than firefighting. I find meaning in that invisible work, where silence is the only sign that anything was done at all.

CocoMine

SKYWALK, 2024.12 – 2026.02

Cozy life simulation SNS, 10K+ users, peak CCU 500–1,000

Team and roleServer content developer in a team of 2 server, 5 client, and 1 UI developers. After the other server developer left mid-project, I owned the server alone. Key technical decisions such as channel distribution and scale-out were reviewed with the CTO before being applied.

GoC#ASP.NET CoreMySQLRedisBigQuery
Login processing time30 s to 3 min10–30 s
Ranking query time10–20 s1–2 s
Item and ranking data processing5–15 s2–6 s

Situation

  • Each login API held its own lock, so sessions queued one after another under load
  • The plaza and village packed all users into a single channel, causing lag and disconnections
  • Every ranking request read MySQL directly, creating heavy load under concurrent requests
  • There was no real-time chat between users
  • The operations team had to ask the dev team every time they needed game data

Task

  • Login stabilization
  • Plaza/village channel distribution
  • New chat server
  • Faster ranking queries
  • Operations tool design

How I solved it

  1. Login bottleneck: less lock contention, independent work in parallel

    Found that the locks attached to each login API were serializing requests. Reduced contention around the request-wide locks and separated independent work so it runs in parallel. The remaining bottleneck was cleared by expanding the DB connection pool and adding missing indexes.

  2. Channel pool: place users in the least-loaded channel

    Gave the plaza and village a pool of 5 channels by default and designed distribution logic that assigns new users to the channel with the fewest users. Per-channel user state is isolated so only users in the same channel interact. Per-channel user counters are protected against race conditions under concurrent joins with Go's sync.Mutex.

  3. Auto scale-out: 5 new channels at 25 of 30

    When all channels approach 25 of their 30-user capacity, 5 channels are provisioned at once. New users are then placed gradually to prevent a thundering herd onto the new channels. The 30-user capacity was confirmed through blind playtesting.

  4. New chat server

    Agreed on the spec with the planning team, then built the chat server from design through implementation. Also added the village and district servers, with interactive items, interaction motions, and an address system inside the village.

  5. Ranking: from direct MySQL reads to Redis

    Contribution and fashion-match scores are written to Redis in real time, and reads go through paging and Redis caching. Ranking views no longer hit the DB repeatedly.

  6. Operations tool and query tuning

    Finalized requirements with the operations team, then designed and built the ops tool on ASP.NET Core. Applied indexing and query optimization to lagging paths, cutting read/update time for large item and ranking data from 5–15 s to 2–6 s.

Result

  • Login time cut from 30 s to 3 min down to 10–30 s, ranking queries from 10–20 s to 1–2 s
  • Single-channel overcrowding in the plaza and village eased by least-loaded placement and auto scale-out
  • Social content expanded with user chat, the village, and the district map

Situation

  • MySQL 5.7 reached end of life in October 2023, ending security patches, so an 8.0 migration was unavoidable
  • Network delays caused 4–5 payment failures a day, or payments that completed without the item being granted
  • The operations team had to ask the dev team for every piece of game data, which slowed decisions
  • Content differed by region, so some errors appeared in only one region

Task

  • MySQL 8.0 migration
  • Payment stabilization
  • Dashboard for operations
  • 4-region maintenance

How I solved it

  1. Payments: retries that never grant twice

    Added automatic retries when a payment fails because of network delay. Before each retry, prior payment records and grant records are cross-checked so an item that was already granted is not granted again, and payments that completed without the item being granted are safely recovered.

  2. MySQL 5.7 to 8.0

    Found the places where 8.0 breaks compatibility, such as the authentication method and GROUP BY handling, fixed the source code, tested, and deployed. Applied indexing and optimization to key queries at the same time.

  3. A dashboard the operations team reads directly

    Agreed on the metrics with the operations team, then built currency, token, and log dashboards with BigQuery and Looker Studio. The team could check data without going through the dev team.

  4. 4-region operations and documentation

    Tracked down and fixed errors caused by region-specific content, and built new content. Documented content and bug lists and kept them current so other developers could quickly understand the operating history.

Result

  • Payment failures dropped from 4–5 per day to 1 every 1–2 weeks
  • After the dashboard launched, one-off data requests turned into feature-driven analytics requests
  • The operations team could identify error-prone periods on their own

C++ Network Game Server Learning Project

Personal project, 2026.07 – present

Builds connection handling step by step from v1 to v6 and reproduces the behavior of each architecture in a GUI

C++20CMakeLinuxWindowsepollIOCPDocker
GitHub
Linux server28,000 concurrent connections
Messages processed560,000
Windows IOCP sustained12,000 connections, 120,000 messages

Goal

  • Build connection handling, network I/O, and multithreading for a C++ game server by hand to strengthen server fundamentals
  • Implement the same feature in several architectures and test them under the same conditions to see where each one hits its limit

How I solved it

  1. Fix each version's limit in the next one

    Started from a server that handles one client at a time, then built thread-per-connection, a reusable thread pool, Linux epoll, and Windows IOCP. Learned how to use threads efficiently as connections grow and how to separate network I/O from application work.

  2. Reliable transfer and shutdown

    Handled partial sends by continuing the remaining data, and used send queues so one user's messages never change order. Implemented a shutdown order for work and threads so the server stops safely even with open connections, and verified pending I/O draining.

  3. Automated checks

    Automated repeated connect/disconnect and server shutdown tests, and checked for memory errors.

  4. Cross-platform GUI for comparing architectures

    One screen controls version selection and launch, up to 200 client connections, individual, delayed, and repeated sends, and Echo response aggregation. It detects the versions and Native/Docker modes the host OS supports, and builds missing binaries with CMake.

Result

  • Load tests exposed work piling up on network-processing threads, defining the next optimization target
  • Built a lab that detects supported modes on macOS, Linux, and Windows and reproduces each architecture in one UI
